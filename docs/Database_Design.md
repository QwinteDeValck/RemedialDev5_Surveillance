# Database Design

## Overview

The application uses PostgreSQL as its primary database. The schema consists of five tables that model users, roles, observations, modification requests, and audit logs. The design prioritizes referential integrity, auditability, and flexibility.

## Relationships

| Parent Table | Child Table | Foreign Key Column | Cardinality |
|--------------|-------------|--------------------|:-----------:|
| roles        | users | users.role_id → roles.id | 1:N |
| users        | observations| observations.created_by → users.id | 1:N |
| users        | observation_requests | observation_requests.requested_by → users.id | 1:N |
| observations | observation_requests | observation_requests.observation_id → observations.id | 1:N |
| users        | audit_log | audit_log.performed_by → users.id | 1:N |

All foreign keys are enforced at the database level with `REFERENCES` constraints. This guarantees referential integrity: an observation cannot reference a non-existent user, and a request cannot reference a non-existent observation. Deleting a referenced user or observation requires handling the dependent rows first.

## Schema Details

### roles

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| id | SERIAL | PRIMARY KEY | Auto-incrementing integer |
| name | VARCHAR(50) | UNIQUE, NOT NULL | USER, MODERATOR, ADMIN, OWNER |
| created_at | TIMESTAMPTZ | DEFAULT NOW() | |

**Unique constraint**: `name` must be unique across all roles.

The table is seeded during initialization and rarely modified. The application defines a numeric level mapping for authorization:

```javascript
const ROLE_LEVELS = { USER: 1, MODERATOR: 2, ADMIN: 3, OWNER: 4 };
```

### users

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| id | UUID | PRIMARY KEY | Generated by `gen_random_uuid()` |
| username | VARCHAR(100) | UNIQUE, NOT NULL | Display name |
| email | VARCHAR(255) | UNIQUE, NOT NULL | Login credential |
| password | VARCHAR(255) | NOT NULL | scrypt hash with 16-byte salt |
| role_id | INTEGER | NOT NULL, FK → roles.id | Default 1 (USER) |
| preferred_city | VARCHAR(100) | NULLABLE | Map default location |
| preferred_latitude | DECIMAL(10,7) | NULLABLE | |
| preferred_longitude | DECIMAL(10,7) | NULLABLE | |
| deleted_at | TIMESTAMPTZ | NULLABLE | Set on account deletion (soft delete) |
| created_at | TIMESTAMPTZ | DEFAULT NOW() | |

**Unique constraints**: `username` and `email` must each be unique across all users. This prevents duplicate accounts and ensures login credentials are unambiguous.

Design decisions:

- **UUID primary keys** prevent enumeration attacks (vs. sequential integers) and simplify distributed ID generation.
- **Soft delete** via `deleted_at` preserves referential integrity. When a user deletes their account, their observations remain in the system. The login endpoint explicitly checks `deleted_at` and rejects deleted accounts.
- **Map preferences** are stored directly on the users table because each user has exactly one preference set. A separate table would introduce unnecessary complexity.

### observations

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| id | UUID | PRIMARY KEY | Generated by `gen_random_uuid()` |
| title | VARCHAR(255) | NOT NULL | |
| category | VARCHAR(100) | NOT NULL | e.g. noise, vehicle, suspicious |
| description | TEXT | NULLABLE | |
| address | TEXT | NOT NULL | Street address for display |
| latitude | DECIMAL(10,7) | NULLABLE | From Nominatim geocoding |
| longitude | DECIMAL(10,7) | NULLABLE | |
| is_public | BOOLEAN | NOT NULL, DEFAULT false | Visibility flag |
| status | VARCHAR(20) | NOT NULL, DEFAULT 'OPEN' | Reserved for future state tracking |
| created_by | UUID | NOT NULL, FK → users.id | |
| closed_at | TIMESTAMPTZ | NULLABLE | Set when an admin closes an observation |
| created_at | TIMESTAMPTZ | DEFAULT NOW() | |

Design decisions:

- **Separate coordinates from address**: The address is human-readable for display; coordinates are stored separately for map rendering. This avoids re-geocoding every time the map loads.
- **Visibility flag (`is_public`)**: All API endpoints filter on this column. Only public observations appear on the map and in public listings. Private observations are only accessible by their creator.
- **`closed_at` vs. DELETE**: Observations are never physically deleted. Setting `closed_at` and `is_public = false` archives the observation while preserving its history.

### observation_requests

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| id | UUID | PRIMARY KEY | |
| observation_id | UUID | NOT NULL, FK → observations.id | |
| requested_by | UUID | NOT NULL, FK → users.id | |
| type | VARCHAR(20) | NOT NULL, CHECK (EDIT, DELETE) | |
| reason | TEXT | NULLABLE | User-provided justification |
| status | VARCHAR(20) | NOT NULL, DEFAULT 'PENDING', CHECK (PENDING, APPROVED, REJECTED) | |
| proposed_title | VARCHAR(255) | NULLABLE | Only for EDIT type |
| proposed_category | VARCHAR(100) | NULLABLE | |
| proposed_description | TEXT | NULLABLE | |
| proposed_address | TEXT | NULLABLE | |
| created_at | TIMESTAMPTZ | DEFAULT NOW() | |

Design decisions:

- **Single table for both EDIT and DELETE**: Rather than separate tables, a `type` column distinguishes the request kind. The `proposed_*` columns are only relevant for EDIT requests; DELETE requests use only the `reason` field. This simplifies queries and keeps the schema normalized.
- **Status workflow**: Requests follow `PENDING → APPROVED | REJECTED`. Once processed, the status is final. The controller checks that only PENDING requests can be acted upon.
- **Approved edits are executed inside a database transaction**: On approval, the controller updates the observation with all non-null proposed fields atomically, ensuring consistency between the request status and the observation data.

### audit_log

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| id | SERIAL | PRIMARY KEY | Auto-incrementing integer |
| action | VARCHAR(100) | NOT NULL | e.g. REQUEST_APPROVE, USER_DEACTIVATE |
| entity_type | VARCHAR(50) | NULLABLE | e.g. user, observation_request |
| entity_id | UUID | NULLABLE | |
| performed_by | UUID | NOT NULL, FK → users.id | |
| details | JSONB | NULLABLE | Arbitrary structured data |
| created_at | TIMESTAMPTZ | DEFAULT NOW() | |

Design decisions:

- **JSONB for details** provides flexibility to store action-specific metadata (e.g., role change old/new values, request type) without adding columns for every possible action type. PostgreSQL's JSONB supports indexing if querying by detail fields becomes necessary.
- **SERIAL primary key** is acceptable here because audit logs are append-only and sequential IDs help with ordering. UUIDs are unnecessary for internal logging.
- **Descending index on `created_at`** ensures efficient retrieval of the most recent entries, which is the primary access pattern for the audit log UI.
- **Immutability**: Audit entries are inserted once and never updated or deleted. This provides a tamper-evident record of administrative actions.

## Database Design Principles

The database was designed according to the following principles:

- **Minimize redundancy**: Data is stored exactly once. Role names live in the `roles` table, user details in `users`, observation data in `observations`. No duplication across tables.
- **Preserve referential integrity**: All relationships are enforced through foreign key constraints. The database guarantees that every `created_by`, `performed_by`, and `observation_id` references a valid row.
- **Support auditing**: The `audit_log` table captures every administrative action with enough context (action type, entity reference, performer, JSONB details) to reconstruct what happened and why.
- **Enable future extensibility**: The `status` column on observations, JSONB `details` on audit logs, and the generic `entity_type`/`entity_id` pattern allow new states and event types without schema migrations.
- **Keep lookup tables normalized**: Roles, request types, and status values are stored as VARCHAR with CHECK constraints rather than enums or separate tables, balancing normalization with simplicity.

## Normalization

The database schema follows **Third Normal Form (3NF)**.

- **Roles are stored in a separate table** rather than as a column on users. This avoids duplicating role names across user rows and makes role renames a single-row update.
- **Observations reference users through a foreign key** (`created_by`) instead of embedding user data. This eliminates redundancy and ensures the creator's information is always current.
- **Observation requests are separated from the observations table**. Storing requests in a dedicated table avoids nullable moderator columns on the observation row and keeps the request lifecycle (PENDING → APPROVED | REJECTED) independent of the observation data.
- **Audit logs are stored independently** of the entities they reference. This preserves immutable historical records that remain meaningful even if the referenced user or observation is later deleted.
- **Proposed changes are stored directly on the request row** rather than in a separate changes table. Since each EDIT request has at most one set of proposed values, a separate table would introduce an unnecessary 1:1 relationship without a normalization benefit.

## Indexes

| Table | Index | Type | Purpose |
|-------|-------|------|---------|
| audit_log | idx_audit_log_created_at | BTREE DESC | Efficient recent-entry queries |

Primary key columns (`id`) are indexed automatically by PostgreSQL. Foreign key columns (`role_id`, `created_by`, `requested_by`, `observation_id`, `performed_by`) are **not** automatically indexed and would benefit from explicit indexes if query performance becomes a concern. The current data volume does not warrant additional indexing beyond the descending index on `audit_log.created_at`.

## Soft Deletes

The application implements soft deletes for both users and observations:

- **Users**: Setting `deleted_at` to the current timestamp marks the account as deleted. The login endpoint rejects deleted accounts. User data is preserved for audit trail continuity.
- **Observations**: Setting `closed_at` and `is_public = false` effectively archives the observation. It remains in the database but is excluded from public queries.

This approach was chosen over physical deletion because:

1. Foreign key relationships remain valid (observations reference their creator).
2. Audit log entries referencing deleted entities remain meaningful.
3. Account recovery is possible by clearing `deleted_at`.
