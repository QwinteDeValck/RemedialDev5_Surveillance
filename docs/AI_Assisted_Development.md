# AI-Assisted Development

## Role of AI in the Project

The assignment requires that AI assists the development of the application while the student remains the architect. This chapter describes how that requirement was fulfilled: what the AI was used for, how prompts were formulated, and how the developer retained control over every change that reached the codebase.

The AI assistant (OpenCode CLI) was used throughout the project as a support tool. It did not design the application, choose the technology stack, define the database schema, or decide the API. Those decisions — the system architecture, the module structure, the authorization model, and the data model — were made manually and are documented in the architecture chapters of this report. The AI's role was to accelerate the mechanical parts of implementation: generating initial code, drafting SQL, proposing refactorings, and improving documentation.

## Division of Responsibility

The project followed a clear separation between what the AI could propose and what the developer decided:

| Responsibility | Held by |
|----------------|---------|
| System architecture and design decisions | Developer |
| Technology selection (Node.js, Express, PostgreSQL, Leaflet) | Developer |
| Database schema and relationships | Developer |
| API design and route structure | Developer |
| Role-based authorization model | Developer |
| Boilerplate code generation | AI, reviewed by developer |
| SQL query drafting | AI, reviewed by developer |
| Express controller scaffolding | AI, reviewed by developer |
| Middleware implementation | AI, reviewed by developer |
| Frontend component generation | AI, reviewed by developer |
| Refactoring suggestions | AI, executed by developer |
| Documentation drafting | AI, verified by developer |

This table reflects a consistent workflow: the AI produced drafts, and the developer reviewed, integrated, tested, and corrected every piece of generated code before it was committed.

## Where AI Was Used

### Boilerplate Code

Routine structural code — database migration files, route registration, controller skeletons, and HTML page scaffolding — was generated by describing the intended behavior in natural language. This removed the repetitive overhead of writing similar blocks for every endpoint, allowing the developer to focus on the logic specific to each feature.

### SQL Queries

Complex database queries, such as the join-based queries that resolve a user's current role, the filtered observation listings, and the paginated audit log query, were drafted with AI assistance. The developer then reviewed the query plans and results against the schema.

### Express Controllers and Middleware

Controllers that implement business logic (registration, observation CRUD, request moderation) and middleware for authentication and authorization were generated as first drafts. These drafts were then aligned with the project's error-response conventions and tested against every relevant scenario.

### Frontend Components

Frontend JavaScript and HTML for the map, observation tables, filter bars, and administration panels were generated as starting points. Styling and role-dependent visibility rules were then adapted manually to match the application's design.

### Documentation Improvements

The architecture chapters of this report were drafted with AI assistance and then corrected against the actual implementation. This served as a verification mechanism: describing the system precisely required checking that the documentation matched the code.

### Refactoring Suggestions

When repeated patterns were identified, the AI was asked to propose consolidations. Several shared utilities in the codebase originated from this process, including the `logAction` audit function, the `authorize` middleware, and the frontend authentication helpers.

## Prompt Examples

The prompts used were short and specific. They described a task, named the relevant files or constraints, and let the developer review the result. The following examples are representative.

> Generate an Express middleware for role validation. It must accept a minimum role name, query the user's current role from the database, and return 403 when the user's role level is insufficient.

> Create a PostgreSQL query that returns public observations with the author's username, ordered by creation date.

> Refactor this controller according to the Single Responsibility Principle. Split the request-handling logic from the database queries.

> Generate a reusable Leaflet map component that renders observation markers from an array of coordinates.

> Write a SQL migration that creates the audit_log table with an action column, a foreign key to users, and a details JSON column.

> Generate the Express route file for the profile endpoints with authentication middleware on every route.

> Suggest a consistent error response format for all controllers, returning status codes 400, 401, 403, and 500 with a descriptive message.

> Draft the validation checks for the registration endpoint: username length, email format, and password requirements.

> Propose a function that inserts an audit log entry and is shared between the admin and profile controllers.

## Prompt Engineering

Prompt engineering refers to the practice of formulating requests to an AI assistant so that the responses are useful and predictable. In this project, three principles guided prompt construction.

**Specificity.** A prompt that named the exact artifact ("middleware for role validation"), the input it receives ("minimum role name"), and the expected behavior ("query the user's current role, return 403") produced a more targeted result than a general request. Vague prompts produced generic code that required more correction.

**Context.** Providing relevant context — the framework in use, the naming conventions of the project, or the name of a file to modify — improved the relevance of the response. The AI did not know the codebase by itself; useful results depended on the developer supplying accurate context.

**Review framing.** Prompts were often phrased as review requests ("Suggest", "Propose", "Refactor") rather than as commands to produce a final implementation. This framed the output as a proposal to be evaluated rather than a finished product to be trusted.

Prompt engineering was a developer skill, not an automated process. The quality of the generated code was directly related to the precision of the prompt, and the developer's understanding of the domain was required to judge whether a response was correct.

## Verification Workflow

Every generated piece of code followed the same review cycle before it was accepted:

1. **Review.** The generated code was read line by line. Errors, inconsistencies, and deviations from project conventions were identified.
2. **Manual integration.** The code was placed into the project structure by hand. Route files were registered, imports were added, and the code was adapted to the existing patterns rather than inserted unchanged.
3. **Testing.** The integrated code was tested through the API and the browser. Success, validation, authentication, and authorization scenarios were exercised.
4. **Refactoring.** Where the generated code was correct but poorly structured, it was refactored to fit the architecture. Duplication was removed and utilities were extracted.

This cycle was applied uniformly. No AI-generated code was committed directly; every change in the repository passed through manual review and testing.

## Why AI Was Treated as an Assistant

The assignment specifies that AI should assist development while the student remains the architect, and that design decisions should remain manual. The project adhered to this for both practical and methodological reasons.

From a practical standpoint, the AI had no access to the running application, the database, or the user's intent. It could not verify that code worked, observe error messages, or judge whether a design fit the requirements. Those activities require human judgment and access to the system under test.

From a methodological standpoint, treating AI as an assistant rather than an autonomous developer preserved the engineering value of the project. The architectural decisions — the choice of MVC, the database-first ordering, the role hierarchy, the audit design — were the substantive parts of the work. Delegating them to the AI would have produced a functioning application without a documented decision process, which contradicts the purpose of a software engineering project.

The resulting arrangement is that the AI accelerated routine coding while the developer retained full responsibility for the design, the integration, and the correctness of the application. This matches the requirement: AI assists, the student architects.
